# Academic ERP - Permanent Architectural Directives & Agent Rules

This repository implements an enterprise-grade College Academic ERP. Any AI agent, developer, or contributor working on this codebase MUST strictly adhere to the following core architectural rules:

## 1. The "Ask Once" Principle (Single Source of Truth)
- **Data Owner Direct Entry**: Every data point must be collected directly from the primary stakeholder:
  - **Students**: Personal details, parental info, qualifying exam history, quota/reservations, address, emergency contacts.
  - **Faculty**: Academic degrees, research publications, awards, teaching experience, bank/payroll details.
  - **Non-Teaching Staff**: Service records, qualifications, administrative designations.
  - **Research Scholars**: Registration ID, thesis title, guide/supervisor, fellowship funding agency, progress milestones.
- **Zero Redundancy**: No module (NAAC, NIRF, Exam Cell, Attendance, Hostel, Library) may re-request data already captured in the master profile.
- **Post-Approval Immutability**: Once approved, live data is locked against direct edits.

## 2. Maker-Checker & Superior Approval Hierarchy
- If any data variable changes, the user must submit a **Data Change Request** (`data_change_requests`) with proposed value, mandatory justification, and optional/required document proof.
- Direct edits to live data are prohibited; changes are committed only after superior approval:
  - **Student** -> Department Faculty Advisor / Class Tutor -> HoD -> Admin
  - **Faculty** -> Head of Department (HoD) -> Principal -> Admin
  - **Non-Teaching Staff** -> Section Head / Administrative Officer -> Principal -> Admin
  - **Research Scholar** -> Research Supervisor -> HoD / Dean -> Admin
  - **Admin Override ("God Mode")**: Admin has authority to review and approve/reject any change at any level.

## 3. Dynamic QR Code & Activation URL Self-Enrollment
- Self-enrollment requires an active token generated by a Superior or Admin (`enrollment_tokens`).
- Token specifies target role, department, batch, expiration window, and scan limits.
- Candidate scans QR or opens link, authenticates via Google (`gami aid` / Gmail ID), and submits a `join_request`.
- Superior verifies applicant against official admission lists and approves the request.
- The approved candidate completes the Onboarding Wizard (Ask Once). Superior reviews the full submission and either approves it into live status or requests corrections with line-item notes.

## 4. Admin "God Mode" & Universal Role Switcher
- The Admin navbar includes a global **Role Simulator / God Mode**:
  - Admin can instantly switch their simulated role to any role (`STUDENT`, `FACULTY`, `HOD`, `RESEARCH_SCHOLAR`, `RESEARCH_SUPERVISOR`, `WARDEN`, `PRINCIPAL`, `STAFF`) to audit and verify that role's exact UI, menus, and permissions.
  - Universal administrative override allows bypassing bottlenecks across all departmental workflows.

## 5. Strict Input UI Standards
- Predefined dropdowns for categorical fields (Blood group, Gender, Religion, Category, Degree).
- Searchable dropdowns for large datasets (State, District, Courses, Post Offices).
- Checkboxes (tick marks) for multi-select options (Reservations, Transport, Hostel, Declarations).
- HTML5 calendar pickers (`<input type="date">`) for all dates.
- Strict regex validation for phone numbers (`^[6-9]\d{9}$`), emails, and URLs.
